## 4. Worked around

- **`.env` sourcing scope for P0-5.** The first implementation sourced the entire `.env` file into the recipe's shell (`set -a; . ./.env; set +a`). This passed the specific P0-5 acceptance test but broke a different, newly-collected test (`test_full_agent_flow`, from P0-4) by shadowing an already-correct `OPENAI_API_KEY` in the shell with a stale placeholder value from `.env`. This was caught by running the full suite, not just the targeted test, after the change - the narrower per-variable-subshell version in the final `Makefile` is the result. Flagging this because it is exactly the kind of "fix that quietly breaks something one test-run away from the one you were looking at" the standing rules ask to watch for.
- **`verifier-state` volume desync.** Mid-phase, a live test (P0-2's step 2) failed with a gRPC `INVALID_ARGUMENT: illegal state` error from the verifier - not a code defect, but the `verifier-state` named Docker volume (persistent) having drifted out of sync with ImmuDB's data (which has no persistent volume in `docker-compose.yml` and resets on every `docker compose down`/`up`), from earlier `down`/`up` cycles in this same working session. Resolved by `docker volume rm compliance-ail_verifier-state` and bringing the stack up fresh. This is the same class of issue the prior audit documented for SPIRE's volumes; it did not recur for SPIRE in this phase, only for the verifier.
- **Docker Desktop and image staleness.** Same as the prior audit: Docker Desktop needed a manual start, and the custom images needed an explicit `docker compose build` before results from the main stack could be trusted, since none of the P0 code changes take effect in a running container until its image is rebuilt.
- **Windows console encoding.** One diagnostic run of the newly-moved `tests/test_epic_3.py` with `-s` (no output capture) crashed with `UnicodeEncodeError` on that file's own `✅` characters, because Windows' default console codepage (cp1252) cannot encode them. The actual gate command (`pytest tests/ -v`, no `-s`) does not hit this - pytest's default output capture insulates it - confirmed by running the identical command with and without `-s`. `PYTHONIOENCODING=utf-8` was used only for the diagnostic run that needed to see live output; it was not added to the `Makefile`, since the real recipe doesn't need it and adding an unrequested workaround for a problem the gate doesn't actually have would be exactly the kind of unasked-for scope creep the standing rules warn against. The crash itself is real and is reported in section 6, not fixed.
- **Nothing else rose to the level of feeling like a pushed-toward redesign.** The closest was P0-4's instruction to "move" the two root scripts with unique coverage: making the move meaningful required fixing their `sys.path`/import style to match every other file in `tests/`, and (for `test_epic_3.py`) correcting an `OPA_URL` that pointed at `/deny` instead of `/allow` as the primary endpoint - a convention the *current* middleware code assumes everywhere else. Both were treated as mechanical relocation necessities, not logic changes, on the same footing as P0-4's `__init__` → `setup_method` fix; nothing about either file's actual assertions (there are none) or test scenarios was altered.
