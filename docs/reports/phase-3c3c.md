## 3. Escalations raised before building

Three, all raised with the evidence in hand and answered before any code was written. All three answers are implemented as given.

**3.1 The fault record is a new ledger record kind, and the verifier holds no writer key.** Every other record carries `writer_signature` inside it, and `tools/ail_verify_bundle.py` refuses a record with none (`writer_signature_missing`, and its own comment says it is "not treated as unsigned-and-fine"). D22's rule is one dedicated long-lived key per writer. The options were a third writer key, an unsigned fault record with a Residual Limits entry, or deferring the fault record entirely.

*Answer taken:* a third writer key. `keys/writer-verifier.key`, generated by the same `make keygen` loop as the other three, mounted read-only into the verifier and nowhere else. An unsigned record whose only job is to qualify another record's standing would be a record this project's own checker refuses.

**3.2 P3c3c-11: carrying the fault in the bundle is a format change.** Measured first: the exporter takes only a key and passes no revision, and `ail-evidence-bundle/2` has four sections with no place for a fault. Adding an always-present one is exactly the move `external_anchor` was at format `/2`, so it is a bump to `/3`. The instruction pre-authorised an escalation here because it is a D18 through D20 decision.

*Answer taken:* a Residual Limits entry only. The format does not change this phase. The entry is in `readME.md` section 5 and the gap is stated as an item rather than left implicit.

**3.3 P3c3c-12: `erase_content` and a committed-unverified tombstone.** Evidence brought, all live on `b9f6a1d` (section 4.6). The instruction's lean was that the delete completes.

*Answer taken:* the delete completes, **after the tombstone is confirmed present in the ledger by an exact read**, rather than on the strength of the response's `tx_id` alone. One extra call on a path that has already failed once, and it separates a stale trust anchor (the record is there) from a record that genuinely is not in the tree. If the confirmation fails, or cannot run, the erasure is refused and the row survives.

### One design question resolved rather than escalated

D36 says the reserve is bound "at first allocation". A ledger that was already allocating before this phase has no first allocation left to catch. The binding therefore attaches to its next allocation, which is the earliest moment available, and a deployment that had already raised its reserve before upgrading binds the raised value. Nothing can retroactively distinguish that case. It is implemented that way, stated in the ADR, and carried in Residual Limits rather than assumed away.

### 6.2 Two existing tests changed, and why neither weakened

**`tests/test_anchored_export.py::test_writes_continue_and_records_are_produced_with_anchoring_broken`** asserted `"anchor-service" not in compose["services"]`. P3c3c-4 puts the service in that file. Absence by name was never the property that mattered; not anchoring is. The assertion is now the mechanism: if the service is present it must be in `AIL_ANCHOR_MODE=reconcile-only`, and it must hold none of the three credentials an anchoring cycle needs (`AIL_ANCHOR_SIGNING_KEY`, `VERIFIER_READ_KEY`, `CONTROL_PLANE_WRITE_KEY`). A future edit restoring the anchoring loop fails this exactly as the absence check would have, and the runtime half of the test (a bundle exported here says `not_anchored`) is untouched.

**`tests/test_audit_ordering.py::test_each_record_kind_is_written_through_the_route_that_matches_it`** kept its parse and had both weaknesses closed. It walks every production module in eight directories rather than two files, and it locates each occurrence of the plain route rather than counting substrings, so `ledger.verifier_url + _PLAIN_ROUTE` in a module with no allowed span is caught. Two measurement probes that deliberately drive both routes are named individually rather than by excluding `tools/`, so a new module there is still caught. **The route-level refusal is the criterion now**; this is the second line.

Four test files that wrote decision records through `POST /write` were updated to the ordered route, because the route now refuses them: `tests/test_anchored_export.py`, `tests/test_evidence_bundle.py`, and `tests/test_audit_ordering.py`'s two backfill fixtures (which now write straight to ImmuDB's own `set`, because "an older build wrote this" is not reachable through any route this build has). Three other files already routed decisions to `/write-ordered` and needed nothing.

## 7. Measurement: P3c3c-10, `total` and the page

The item asked for a number once duplicates were gone, and for the card to be left alone. Both done.

**On a virgin ledger, twelve decisions and nothing else:**

```
  limit=5     rows=5   total=12  has_more=true
  limit=12    rows=12  total=12  has_more=false
  limit=200   rows=12  total=12  has_more=false
  limit=2500  rows=12  total=12  has_more=false
```

**They agree exactly.** At any limit that reaches the ledger, `len(entries) == total`. The disagreement the red team recorded (`rows=2499 total=10`, and the reproduction's `page rows 10 against total 5`) needed duplicate index rows to exist, and P3c3c-5 removed those.

**One orphaned write-ahead intent added, nothing else changed:**

```
  limit=5     rows=6   total=12  has_more=true
  limit=200   rows=13  total=12  has_more=false
```

The remaining disagreement is exactly one per orphaned intent, in the direction the docstring and README already state: `total` counts `tool_call:` keys, and a synthesized row for an intent with no completion record lives under `tool_call_intent:`, so no key count can include it. It is appended after the limit is applied, which is why `rows` exceeds `limit` at `limit=5` too.

**On the ledger this phase's own suite left behind** (2734 decision records, 2750 decision-view rows, 2749 distinct keys):

```
  limit=2500  rows=2501  total=2734  has_more=true
```

2499 page rows plus 2 orphaned intents, against a ledger of 2734. Both differences are the two documented causes and neither is a duplicate. One duplicated index row survives in that view, left by tests that zadd by hand into a ledger reused across a dozen runs; it is a property of that ledger, not of the write path, and a fresh stack has none.

**The card is unchanged**, per the item.

## 11. Could not verify

1. **Whether a bundle could carry a fault without a format bump was not explored past the point the escalation needed.** `verifiable/get` accepts `keyRequest.atRevision`, measured, so a prior fault is provable at the ledger; the exporter passes no revision and the bundle has no section for one. That is enough to establish the answer is "not without a format change", which is what was escalated. What a `/3` format would look like was not designed.

2. **The one write that needs no proof is bounded by three mechanisms, and two of them are asserted structurally rather than exercised.** `_set_without_verification` refusing a non-fault record and having exactly one caller are asserted by parsing `verifier/main.py`, because there is no argument a caller can arrange that reaches it live. The third bound, `POST /write` refusing a `ledger_fault` from outside, is exercised live.

3. **The reserve binding on a ledger that was already allocating was not exercised on a real pre-3c-3c ledger.** Every stack in this phase was built from a checkout that has D36 in it, so the "binding attaches to the next allocation" path was reasoned about and implemented, not run against a ledger written by the previous build. What is exercised is the fresh-ledger case and every reader's refusal.

4. **The unexplained ordering-suite failure the red team could not reproduce is still unexplained.** It did not recur in any run this phase, including a cold-start full suite and a dozen partial runs. Bounded no further than the red team left it.

5. **The local full suite does not pass on this host, before or after this change, for two reasons that are not about the code** (`sigstore` cannot be installed into the host Python, and the tests that drive `decision_service/main.py` in-process cannot resolve compose service names or hold the verifier's write key). 67 failed locally against 309 passed.
