### X4 — HOLDS

**Self-certifying bundle, `attack_x4.py`:** generated an unrelated ECDSA keypair, forged an entire anchor "signed" by that key, and set both `signing_key.fingerprint` and `proof.signing_key_fingerprint` to the attacker's own fingerprint (every field a self-certifying bundle would need):
```
$ python attack_x4.py
[X4.A self-certifying bundle (attacker key+sig+fp), checked against REAL key] -> key_mismatch
[X4.A' same forged bundle, checked against unrelated OTHER key]              -> key_mismatch
[X4.B forged bundle, checked against the ATTACKER's OWN key (operator error)] -> signature_failure
```
Refused before any proof ran, against both a checker holding the real key and one holding a wholly unrelated third key. X4.B is included to distinguish a real gap from operator error: even if a checker were (wrongly) pointed at the attacker's own key, the forged anchor still fails `signature_failure`, because the checker faithfully verifies against whatever key it is given rather than trusting anything the bundle claims about itself.

**Fingerprint comparison strictness:**
```
uppercased hex                          -> key_mismatch
uppercased algorithm prefix (SHA256:)   -> key_mismatch
truncated to 15 chars                   -> key_mismatch
trailing garbage appended               -> key_mismatch
wrong algorithm label, same hex (md5:)  -> key_mismatch
```
Exact Python string equality (`tools/ail_verify_bundle.py:304-305`); no case-insensitive, prefix, or substring comparison exists to exploit.

**Key path independence, confirmed by source, not merely read:** `load_key(key_path)` (`tools/ail_verify_bundle.py:194-206`) takes exactly one parameter, `key_path`; its body references only that parameter and the standard library. No `Path(...)` construction exists anywhere in `verify_bundle()` outside `load_key()`. ## 6. Findings outside X1-X8

1. **The bundle format has no closed schema — arbitrary undefined fields are silently ignored, including a spoofed top-level `"verified": true`.** Not a break of X2 (the checker's own verdict is computed independently and never reads unknown fields, confirmed live in `attack_x2.py`'s X2.7), but a real risk for any *other* consumer of a bundle file that does not run `tools/ail_verify_bundle.py` and instead eyeballs the JSON or greps for a `"verified"` key — a forged bundle can carry a `"verified": true` field that means nothing to the real checker but could mislead a human or a naive script. Neither `readME.md` §3.4.1 nor ADR-0010 states that the format rejects (or should be treated as rejecting) fields it does not define.
2. **A bundle exported before erasure and replayed after erasure displays a stale `"content_state":"present"`** in its human-readable, checker-verified `record.value`, with nothing in the bundle or its documentation flagging that the live system's own view of that same call has since changed to `"erased"` (live-confirmed, §X6). This compounds finding 2 in this section and X6's own REFUTED verdict: a bundle is a snapshot, and nothing states that plainly for the one field (`content_state`) whose meaning is most likely to change out from under it.
3. **The read credential gating `/audit` and `/audit/bundle` is a single global secret with no tenant scoping at all** — `control_plane/main.py::get_audit` scans every `tool_call:` key in the entire `defaultdb`, with no `tenant_id` filter anywhere in the query or the response. This means X5's own "can a caller export a record belonging to a tenant whose audit view it could not read" sub-question has a vacuous answer under the current architecture: there is no tenant-scoped audit view to be excluded from in the first place, for either `/audit` or `/audit/bundle` — both are equally, globally permissive to any holder of the one read key. Consistent with, and not contradicting, project memory's already-noted "README §4.5 multi-tenant demo does not work as documented" — this is the same underlying architectural gap viewed from the evidence-bundle angle, not a new one.
