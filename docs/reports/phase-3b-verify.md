## A2. Y3's direction-rejection guard, against a live stack

**The attack.** Capture a checkpoint from `GET /state`, *then* write a record,
so the anchor genuinely precedes the record, and ask the live `POST /verify`
for the dual proof anyway. Driven over raw HTTP against the running verifier
rather than through pytest, so the endpoint's actual response body is what is
reported.

```
$ python /attack/a2_attack.py <repo>

=== attack 1: ask /verify for a proof from a record to an EARLIER anchor ===
{
  "verified": false,
  "tx_id": null,
  "value": null,
  "timestamp": null,
  "state_id": null,
  "detail": "the supplied anchor is at tx 1, which precedes the record at tx 2; a
             checkpoint cannot corroborate a record written after it",
  "error_class": "anchor_precedes_record",
  "proof_material": null
}
verified: False | error_class: anchor_precedes_record
proof_material returned: None

=== attack 2: same, several transactions apart ===
anchor tx_id = 1, record tx_id = 6 (gap 5)
verified: False | error_class: anchor_precedes_record | proof_material: None
detail: the supplied anchor is at tx 1, which precedes the record at tx 6; a
        checkpoint cannot corroborate a record written after it

=== control: the ALLOWED direction (anchor at or after the record) still works ===

  prove_since_tx: 6 entry_tx_id: 2
```

Three things are established that reading alone could not settle. The guard
fires. It fires **by name**, so a caller can tell this apart from a record that
simply failed to verify. And `proof_material` is `null` on the refusal, so a
legitimate read-credential holder who deliberately asks for the forbidden
pairing gets nothing back to work with, which is the assertion
`test_an_anchor_older_than_the_record_is_refused_by_name` makes and which was
previously unexecuted. The control case confirms the guard is not simply
refusing everything.

The Y2 fingerprint variants need a note on method. A fingerprint rewritten
*after* signing is just a broken signature and proves nothing about the lookup,
so each variant here was signed **with the variant already inside the signed
bytes**: the signature is genuine, the record is genuinely committed, and only
the lookup string differs. Every one misses, so the lookup really is
exact-string with no normalization anywhere, established against the real
checker rather than a port.

The deny-list ordering is likewise structural rather than lucky. A genuinely
valid record from a denied key is refused `writer_key_revoked`, and so is a
*tampered* record from the same key, so revocation is decided before signature
validity is ever considered.

**Two accepted cases, both already reported by the sandboxed session, both now
confirmed against the real checker rather than a port.** ECDSA signature
malleability (`y1_23`: the same message, the same signer, an alternate valid
encoding of the same signature, asserting nothing new), and a deny-list entry
that differs from the real fingerprint only by case or trailing whitespace.
Neither is bundle-content-driven; the second is an operator-transcription risk.
Both remain findings, not refutations.

### Y3's digest-binding leg, and a difference worth naming

The sandboxed session ran Y3's digest-binding attacks against a port of
`verify_external_anchor` alone and saw them refused at the digest comparison.
Against the **whole** checker they are refused earlier:

```
y3_01_source_state_tx_id    FAILED [signature_failure] the bundle's trust anchor
                                   (tx 3) is not signed by the supplied key
y3_02_source_state_db       FAILED [signature_failure] the bundle's trust anchor
                                   (tx 2) is not signed by the supplied key
y3_03_source_state_tx_hash  FAILED [signature_failure] the bundle's trust anchor
                                   (tx 2) is not signed by the supplied key
y3_04_genuine_but_other_signed_state
                            FAILED [consistency_failure] immudb-py rejected a proof
```

Editing `proof.source_state` breaks ImmuDB's own state signature at step 3,
long before step 10's digest comparison is reached. `y3_04` was built
specifically to get past that, substituting a *genuinely ImmuDB-signed but
different* state (`fault.json`'s, at tx 4); it then dies at the dual proof
instead. So in the full checker the digest-binding comparison is shadowed by
two earlier, independent checks. That is defense in depth working as intended,
not a gap, but it is a real difference from the sandboxed transcript and is
recorded as one.

## B1. The downgrade disclosure

**Which of the two options was taken: the disclosure was added to
`readME.md` §5.** The row was not re-cited.

The reason is what the row's own Kind column says. It reads `Residual Limits +
command`, and Residual Limits means `readME.md` §5 by convention everywhere
else in that table (four other rows cite it the same way). Re-pointing the row
at `docs/reports/phase-3b.md` would make the table accurate and leave the
substance of the finding untouched: an operator reading the shipped
documentation would still not learn that a bundle's `not_anchored` may be a
downgrade rather than a fact. The finding is that the disclosure is missing
where a reader would look for it, not that a citation is untidy. So the
disclosure now exists.

Before, verified by exhaustive grep over the whole file:

```
$ grep -ni "downgrad\|not_anchored\|relabel" readME.md

      external_anchor.state: "not_anchored" and says so in words ...

```

Two hits, both about the honest unanchored case, neither about the downgrade.
`readME.md` §5 (Residual Limits, lines 506 to 524) contained fifteen bullets,
three of them the Phase 3b ones P3b-6 added (writer signature, anchor
permanence, library seam), and no fourth about the downgrade.

**The edit.** A sixteenth bullet was added to §5, placed with the other Phase
3b entries, immediately after the library-seam bullet. It states the
limitation, says why it cannot be fixed inside the format, names
`tools/bundle_byte_sweep.py` pass 3 as where it is measured, and states the
bound that makes it survivable: downgrading only ever removes a claim, and
every direction that would *add* one is refused by name. The bound is not
asserted, it is the executed result of A1 above (`malformed_bundle` for a bare
relabel, `anchor_failure` for a spliced or foreign entry), so the bullet says
what this pass actually demonstrated. It also tells a reader what to do
instead: ask `GET /anchors/latest` or the log, not the bundle.

# Test suite and CI


## Local run, against the live stack

```
$ python -m pytest tests/ -q
15 failed, 271 passed, 9 skipped, 1 warning in 990.70s (0:16:30)
```

All 15 local failures are host-environment artifacts of this pass, not code
defects, and each was diagnosed rather than waved away.

**Fourteen are the host's missing `sigstore`.** Every one is an anchored-bundle
check, and every one fails identically:

```
E  ail_verify_bundle.BundleCheckFailed: anchor_unchecked: checking an anchored
   bundle needs sigstore-python installed (pip install sigstore==4.5.0):
   No module named 'sigstore'
```

`sigstore` cannot be installed into this host's Python: it upgrades
`cryptography` past `spiffe==0.2.5`'s own pin, and its TUF client calls
`os.symlink`, which Windows refuses without elevation. That is why every
anchored-bundle result in Part A was produced inside the Linux container
instead, where `sigstore==4.5.0` is present and these same checks run. CI runs
on `ubuntu-latest` and installs `requirements-test.txt`, which pins
`sigstore==4.5.0`, so these fourteen are green there.

**The fifteenth is pollution this pass caused.**
`test_dashboard_auth.py::test_read_credentialed_get_audit_succeeds` times out
against its own hardcoded `timeout=10`. Part A wrote 33 attack records to the
live ledger, and `/audit` walks every entry:

```
control-plane /audit: 200  entries 101  in 11.3s
dashboard /api/audit: 200               in 17.6s
```

The route answers correctly, it is simply slower than 10 seconds with 101
entries in the ledger. On a clean stack, which is what CI brings up
(`docker compose down -v` first, per the `test-integration` target), the ledger
holds only what the suite itself writes.

Worth recording separately, because it is a real observation and not only an
artifact: `/audit` costs one verifier round trip per entry, so it is linear in
ledger size, and 101 entries is already enough to exceed a 10 second client
timeout on this hardware. That is not a claim failure and no mapping row
asserts otherwise, but it is a scaling property nothing currently measures.
